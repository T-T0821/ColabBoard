# ベンチマーク

グラボード の「要素が増えても軽い」を数字で確かめるための手順と結果。
ボードは `Board::demo(n)`(決まった乱数で付箋・図形・楕円を格子状に並べたもの)で作るので、
同じマシンなら何度測っても同じ条件になる。

## 1. CPU 側の処理時間(`board-bench`)

```sh
cargo run -p board-bench --release                                 # 1 万 / 10 万 / 100 万要素
cargo run -p board-bench --release -- --sizes 100000 --json out.json
```

各項目を複数回測って中央値を出す。「素朴な方法」は全要素を順に調べるやり方(空間インデックス導入前の実装)で、
同じ実行の中で比べている。

測定環境: クラウドの Linux コンテナ(Intel Xeon 2.1 GHz、4 コア)、Rust 1.97、`--release`。2026-10-31 計測。

読み方:

- **ヒットテスト・画面内の要素・範囲選択** は空間インデックス(一辺 256 のグリッド)で画面付近だけを調べるので、
  要素数が 100 倍になってもほとんど変わらない。素朴な方法は要素数に比例して遅くなる
- **毎フレームのカリング** は、描画順のまま 256 個ずつに分けたブロックの外接矩形を画面と比べるだけ。
  100 万要素でも数 µs で、GPU に渡すインスタンスは等倍なら全体の 1% 未満になる
- **初回同期の取り込み** は、サーバーから届いたボード全体(yrs の更新)を参加者が取り込む時間
- **要素 1 個の移動** はドラッグ中の 1 フレームぶんの処理(yrs への書き込み、表示用データと空間インデックスの更新、
  送信データの取り出し)

### 初回同期の改善

変更前は、ボード全体を取り込むときに要素を 1 個ずつ描画順の位置へ挿入し直していたため、要素数の 2 乗の時間がかかっていた。
まとめて届いた変更は 1 回のマージで並べるようにした。同じマシンで `push_many` → `encode_diff` → 別のボードで `apply_remote`
を測った結果:

| 要素数 | 変更前(main) | 変更後 | データ量 |
| ---: | ---: | ---: | ---: |
| 1 万 | 0.72 s | 0.17 s | 2.8 MB |
| 3 万 | 8.8 s | 0.51 s | 8.4 MB |
| 10 万 | 約 99〜119 s | 2.1 s | 28 MB |

(取り込み側の時間。変更前は要素数が 3 倍で時間が約 12 倍になっていた。残りの大半は yrs 自体の取り込みと、要素の読み出し)

## 2. ブラウザでの描画(`?bench`)

ビルドしたクライアントを `?bench&n=100000` のように開くと、決まった手順でカメラを動かしながら毎フレーム描画し、
結果を HUD と `window.__benchResult`(JSON)に出す。

| 区間 | 内容 |
| --- | --- |
| `pan_100` | 等倍で画面 20 枚分を横に流し見る(240 フレーム) |
| `zoom_out` | 等倍から全体表示まで縮小する(240 フレーム) |
| `pan_overview` | 全体表示(最小倍率)のまま動かす(120 フレーム) |

記録する値:

- `frame_ms`: フレーム間隔(requestAnimationFrame の間隔。画面のリフレッシュレートが上限)
- `cpu_ms`: CPU 側の描画処理(カリング・コマンド作成・提出)
- `gpu_done_ms`: 提出してから GPU が描き終えるまで(WebGPU の完了通知)
- `drawn_instances`: ブロックカリングの後に頂点シェーダへ渡したインスタンス数
- `timings_ms`: 起動の節目(WASM 開始、GPU 準備完了、最初のフレーム、初回同期)

自動で測るには Playwright を使う:

```sh
(cd crates/board-web && trunk build --release)
node tools/bench-web.mjs --sizes 10000,100000,1000000                 # ヘッドレス(WebGL2)
node tools/bench-web.mjs --sizes 100000,1000000 --headed --webgpu     # 実機の GPU で
node tools/bench-web.mjs --sizes 100000 --nocull                      # ブロックカリングなしと比べる
```

**GPU の実力は実機で測ること。** ヘッドレスの Chromium は多くの環境で GPU を使わず、WebGL2 を CPU(SwiftShader)で描く。
その場合の fps はソフトウェア描画の速さで、GPU の速さではない。ただし同じ環境での「カリングあり/なし」の比較には使える。

### 結果(ヘッドレス Chromium、WebGL2 を CPU で描画、480×270)

ソフトウェア描画なので絶対値は小さいが、同じ環境で `--nocull` と比べるとブロックカリングの効果がわかる。

| 要素数 | 区間 | カリングあり | カリングなし | 頂点シェーダに渡した数(あり / なし) |
| ---: | --- | ---: | ---: | ---: |
| 1 万 | pan_100 | 41 fps | 7 fps | 256 / 10,000 |
| 1 万 | zoom_out | 22 fps | 7 fps | 1,639 / 10,000 |
| 3 万 | pan_100 | 54 fps | 3 fps | 768 / 30,000 |
| 3 万 | zoom_out | 19 fps | 3 fps | 2,695 / 30,000 |
| 3 万 | pan_overview | 5 fps | 3 fps | 9,594 / 30,000 |

10 万・100 万要素はカリングありなら最後まで描けた(100 万要素で pan_100 41 fps、描いたのは平均 1,280 個)が、
カリングなしは 10 万要素で 1 回の計測(630 フレーム)が 8 分以内に終わらなかった。

実機の GPU での値は `node tools/bench-web.mjs --headed --webgpu` で測って、ここに追記する。

## 3. 読み込みの軽さ(初回表示)

ヘッドレス Chromium で、キャッシュなし・Service Worker なし(`?room=…&nosw&webgl`)で開き、
最初のフレームを描くまでの時間(`window.__colabboardTimings.first_frame`)と転送量を測った。
回線は CDP で 20 Mbps / 40 ms(4G 相当)に絞った。3 回のうち 2・3 回目の値(1 回目はブラウザの起動を含む)。

| | 転送量 | 最初のフレーム |
| --- | --- | --- |
| 変更前(wasm 9.4 MB を圧縮せず配信) | 9.66 MB | 4.6〜4.9 秒 |
| 変更後(PDF を別 wasm に、brotli で配信) | 1.80 MB | 1.4〜1.5 秒 |
| 変更後 + その後の機能追加(Excel・draw.io 取り込みなど、本体 wasm 7.6 MB) | 2.21 MB | 1.7 秒 |

- PDF の取り込み(hayro)を別の wasm(`board-pdf_bg.wasm`、3.3 MB / brotli 0.9 MB)にし、PDF が貼られたときに Web Worker で読み込む。本体の wasm は 9.4 MB → 6.4 MB
- `trunk build --release` の後に `tools/precompress` が `.br` / `.gz` を作り、サーバーはブラウザが受け取れる形式をそのまま返す。本体の wasm は brotli で 1.76 MB
- 日本語フォント(2.8 MB / brotli 1.4 MB)は以前から最初のフレームの後に読み込んでいる(読み込むまで文字以外を描く)
